# Technical Defense PPT

Treat a deck as a decision-support and defense artifact: every page must state one defensible conclusion, show the right material evidence, and remain credible under questioning.

## Required workflow

1. Read `references/production-system.md` before a new deck or major redesign. Build the asset packet and page-to-asset map **before layout**.
2. Complete the page lock in that reference before each page: claim boundary, hero/support/finish assets, exact crop, figure source, and adjacent-page differentiation.
3. For process, architecture, algorithm, state, or communication pages, follow the topology rules and prefer generated SVG/Graphviz/Matplotlib figures for complex relations.
4. Export slide images and pass the review gate before showing a preview or final deck.

## Asset-first, one-pass behavior

- Scan user-provided folders for photos, video frames, screenshots, maps, logs, tables, documents, and code output. Create one consolidated missing-material request or perform a targeted search/generation action; do not stop at every page for another asset.
- Every normal slide requires a **dominant proof anchor**, a materially distinct **supporting layer**, and an **editorial finish layer**. A muted technical background can occupy unused paper space only when it is derived from relevant material and remains under readable content.
- Build one page at a time from the latest approved PPTX. Internally render, inspect, score, and rebuild until it passes. Show the user one polished candidate rather than a rough layout that will need decorative rescue later.
- Do not ask the user for coordinates, radii, or arbitrary RGB choices. Ask only about a missing real asset, disputed fact, required page order, or explicit visual reference.
- Preserve the named source deck. Make a new preview copy and modify only requested pages plus directly affected neighbors. Keep the newest three disposable preview versions.

## Evidence and claim discipline

Use this progression: `problem → design choice / mechanism → verified evidence → boundary / next validation`.

- Clearly distinguish controlled-task validation, repeatable core mechanism, transferable architecture, contextual application potential, and operational deployment.
- Project-owned photos, logs, clips, tables, and generated technical figures are primary evidence. External or generated imagery is contextual/editorial material unless clearly labeled otherwise.
- Never make a controlled test environment stand in for proof of field deployment. It can still validly demonstrate a repeatable technical loop and reusable method.

## Visual rules

- Vary visual grammar by evidence role: documentary split, material dossier, technical atlas, proof topology, cinematic video stage, test record, editorial conclusion.
- Do not make every page a card grid. Avoid repeated corner brackets, pseudo-devices built from shapes, thick-arrow box flows, random small geometry, and identical large fills.
- Richness comes first from imagery, crop, scale, type, material contrast, formal figures, and clear visual hierarchy — not from arbitrary colors or decorations.
- Use a local dark plate only where a map, log, video frame, or technical screen needs contrast. Keep the overall palette coherent and restrained.

## Preview / delivery gate

Before delivery, export and inspect all modified slides. Reject any page that is sparse without intentional pause, lacks its hero/support/finish trio, repeats an adjacent composition without a series reason, has unreadable evidence, or cannot be explained in its timed speaking beat.

Report the output path, changed pages, strengthened/narrowed claims, asset placeholders, and unresolved evidence/Q&A items.
