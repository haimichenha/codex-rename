# Resume Builder

交付可投递的版本化简历：先锁定用户认可的视觉母版，再完整保留事实，再有依据地取舍内容，最后在 PDF 中验证阅读与版式。用户提供的原始简历、证书、照片和项目说明均是输入，不得直接覆盖、凭文件名补造经历，或把用户已经认可的版式重建成另一套“脚本审美”。

## 最高优先级：用户认可母版优先

当用户说“这个不是很好吗”“就按这个继续”“差不多就是这样”或给出某个 `.pdf/.docx` 作为示例时：

1. 将该文件登记为**母版基线**，后续只做内容级或局部版式微调；不要从零重建整体版式。
2. 先定位同名或相近 `.docx` 源文件；若只有 PDF，先询问是否按 PDF 视觉复刻，不得假装已有可编辑源。
3. 修改前输出差异计划：`保留不动的版式元素 / 只调整的内容 / 不再触碰的区域`。
4. 每次大改后做母版一致性审计：页眉、照片、色彩、栏目比例、正文密度和空白必须与母版接近。
5. 若脚本生成版本与用户认可版本视觉差异明显，立即回滚到认可母版；不要继续沿错误版本迭代。

## 工作区与基线

1. 运行 `scripts/init_resume_workspace.py <workspace>`；将模板、原简历、资料和照片复制到工作区，保留原件。
2. 在 `brief/` 记录目标岗位、投递语种、是否一页、是否需要照片、地点/到岗时间和用户明确的取舍。
3. 将每项教育、奖项、项目、职责、指标和链接填入 `evidence/material-ledger.md`。区分：可证实事实、用户口述待确认、不可写入的推测。
4. 先建立版本号规则：`姓名_方向_实习简历_v1.docx/.pdf`。原件、已确认版、正在打开的文件一律另存，不覆盖。
5. 清理文件前必须列出将删除的文件名，并排除：用户认可版、最新可用版、母版、同名 PDF/DOCX、模板、照片、证书和资料台账。不得把“实验版”默认视为垃圾；只有用户明确说某个版本可以删，或已有更新版且用户确认无用，才删除。

没有模板时，先收集 3–5 个同岗位简历作为**版式参考**，比较信息区、照片、项目密度、字号、页数与链接呈现；不复制他人的身份信息、照片、工作经历或自我评价。

## 内容保留与项目写法

在改写前先做“保留清单”和“差异清单”：每条用户已给出的职责、技术细节、可验证指标、日期、奖项、团队账号、部署证明和项目 URL 都要有去处。不得为了“简洁”“美观”或“一页”擅自丢弃核心职责；若一页放不下，先与用户确认项目优先级和删减项。

- 获奖项目：写清奖项/级别、时间、个人角色、承担模块、关键动作和协作边界。
- 个人项目：以 `场景 → 自己完成的链路 → 技术/工具 → 验证结果` 组织；无验证则如实写“实现/调试”，不编造性能数据。
- 技术栈：每个重要技能至少连接一个项目或课程实践；不要只罗列关键词。
- 纸质简历：项目地址直接写完整可访问 URL，避免只有“GitHub”锚文本。
- 不写未证实的岗位、社会经历、证书、分数、团队负责人身份或量化结果。
- 当用户提供一段完整简历文本时，以该文本为主事实源；先排版承载，不要重新摘要成短版。若必须压缩，保留 P 编号、职责、指标、奖项和链接索引。

## 一页版式与视觉约束

用户明确要求一页时，将其作为验收硬约束，不主动改为主简历加附页，也不以“高级感”为由删除项目、职责或证明入口。局部微调先去重复说明、调整对齐和间距，不换栏式或重建母版。团队项目的个人角色（如“项目成员”）应显眼且准确，日期、奖项、职责摘要另行，不能把所有信息挤在标题后的小字里。

纸质与电子兼用的项目链接，采用“编号＋项目简称｜完整 URL”逐行对齐；团队主页与项目仓库区分标注。显示文字保留完整地址，电子超链接指向同一地址，不以仅可点击的简称替代。空间充足时可用分格布局，但不能为格子截断网址或压到难以阅读。不要把“打印保留”“点击查看”“编号对应正文”等制作提示放入成品。

默认先做一页；只有经历本身足够且岗位需要时再扩展至两页。调整顺序是：项目优先级 → 句子密度 → 段落间距 → 字号，不能一开始把所有字体压得过小。

- 优先黑、深灰、浅灰和留白。默认文字 `#202020`，标题区可用 `#303030`，细分隔线 `#D9D9D9`。
- 禁止把每个分区做成高饱和蓝线、蓝色图标和大块蓝填充；最多保留一种低饱和强调色，并只用于少量层级提示。
- 分区标题、日期、项目角色和链接使用统一字号/字重；少量细灰线即可，不为每段重复画框。
- 高信息密度时使用两栏主体（左：教育/奖项/能力，右：项目）或单栏项目优先；先在 PDF 中确认可读性。
- 对外投递版不放内部管理地址、私密后台链接、令牌、家庭住址等不必要信息。

完整规范见 `references/resume-layout-policy.md`。

## 照片：先选“稳定”还是“视觉自由”

不要把嵌入型照片当作默认答案。它稳定但受单元格尺寸约束，可能让照片与标题块比例不协调。若用户说照片要“浮于文字上方”“显得大”“高度略高于填充”，默认采用视觉优先，不再自动改回嵌入型。记录选择及尺寸，不要在后续版本里无故切换。

### 视觉优先（适合照片略高于深色标题块）

1. 用一行两列的**无边框表格**只负责标题区的网格、左侧深灰填充和右侧留白；照片不受右侧单元格尺寸限制。
2. 将照片设为“浮于文字上方”，使用表格列线作为视觉基准，手动调整大小与位置；照片可高于或低于左侧深灰块，但不得压住姓名、联系方式或正文。
3. 在“布局/更多布局选项”中固定相对页面或页边距的位置，启用“锁定锚点/固定页面位置”（名称随 Word/WPS 版本变化）；在 `qa/revision-log.md` 记录宽高与横纵位置。
4. 每次调整后都导出 PDF；Word 与 PDF 均通过后才锁定。不要依赖自动“对象对齐”按钮处理表格和浮动照片的混合布局。

### 稳定优先（照片与标题块齐平时）

1. 将照片设为“嵌入型”，放入右侧单元格唯一段落；段落水平居中（`Ctrl+E`），单元格设置“垂直居中”。
2. 用“表格工具 → 布局”调整右列宽度、行高和单元格边距；用“图片格式 → 大小”改照片尺寸。嵌入型图片的“对象对齐”按钮禁用是正常现象。

当前用户明确认为嵌入型大小不协调时，采用**视觉优先**方案；表格仍用于建立网格和深色块，不强迫照片嵌入单元格。若 Word 中对象对齐按钮不可用，不要改成嵌入式来“修复”；应使用表格线、绘图网格、更多布局选项和手动坐标微调。

## 渲染与交付

1. 导出 PDF；用 `scripts/check_resume_pdf.py <pdf> --expect-pages 1` 检查页数。
2. 逐页检查：页边距、标题与照片对齐、段落断行、项目链接、证书名称、空白区、照片裁切、文字是否过小、是否仍有多余蓝线/填充。
3. 维护 `qa/revision-log.md`：`用户反馈 → 修改项 → 输出版本 → PDF 检查结果 → 与母版差异`。不得用新版本覆盖上一确认版。
4. 交付 `.docx` 与同版本 `.pdf`，并指出最终版本与仍待用户确认的事实。

明文链接版额外核对：每个预期 URL 同时存在于 PDF 可见文本和超链接注释中；仅检查链接数量不够。可向检查脚本重复传入 `--expect-url <URL>`，并用 `--forbid-text <制作提示>` 检查遗漏的提示。自动检查不证明网页可访问或打印字号可读，仍须查看实际渲染。向技能仓库发布时仅上传通用规则和通用工具，不上传个人简历、照片、联系方式、私有链接台账或含硬编码个人资料的生成脚本。

使用 `references/material-ledger-template.md` 建台账；需要可复用的版式和照片规则时读取 `references/resume-layout-policy.md`。
